# 世界人生 — 模拟引擎、LLM 与万人规模技术设计 v1.0

**本文件是提议的工程架构，不是既有仓库的代码审计。** 现有仓库 `/home/rust1/projects/world-simulator` 未挂载在当前运行环境；我们只能根据 Codex 的报告确定它*声称*拥有若干机制，不能证明它的真实性或质量。

## 1. 最重要的架构决定：一个可裁决的世界，两个精度层，两个内容入口

不建议从头引入第二个“AI 世界状态”或多个互相抢数据库写权限的模拟器。唯一权威状态由 World Runtime 管理；宏观人口/经济结算与具名人物详细行为是**同一世界两种精度**，通过守恒账本连接。

两种内容入口：

1. **机制内容**：可执行的行动、制度、场所和事件族，来自预置参考机制及 LLM 生成内容，通过版本化 DSL/规则 API 执行。
2. **个人出生契约**：LLM 深度理解具体孩子与祝愿生成的潜质、条件式策略、特殊能力，针对人物生效；它只能使用相同的世界行为与结算机制。

History Director 是第三种**提案来源**，不是另一个拥有真实历史的世界引擎。普通 LLM 决策和 Director 都只提交有条件、限定作用范围、可追溯的世界变更提案。

## 2. 明确数据模型及不变量

### 2.1 主要实体及字段

```text
World       {id, calendar, seed, time_policy, current_date, epoch, ruleset_version,
             director_policy, baseline_source_set, status}
Person      {id, world_id, born_at, died_at?, name, sex_and_body, location_id,
             household_id?, guardian_ids[], life_program_version, health,
             dispositions, commitments[], belief_ids[], roles[], provenance}
PopulationCell {id, region, cohort, status_class, job_class, household_class,
                aggregate_count, vital_rates, flows, economy_links}
Household   {id, residence_id, members[], guardianships[], income_accounts,
             expense_obligations, assets, liabilities, sharing_rules}
Place       {id, geo_location, kind, capacity, ownership, offered_actions[],
             institution_id?, availability_calendar}
Relation    {id, a, b, relation_kind, start, end?, commitments, shared_history_ids[],
             a_to_b_beliefs, b_to_a_beliefs}
Organization{id, kind, members, positions, authority_rules, funds, property,
             processes, projects, geographic_scope, decision_rules}
Position    {id, holder_person, org, entitlement, obligation, authority, start, end?}
Project     {id, owner, objective, participants, resources, state, stage,
             deadline?, blockers[], next_actions[], audit_history[]}
Interaction {id, initiator, counterparties, proposal, negotiation_state,
             expirations, knowledge_visibility, linked_project}
Knowledge   {id, holder, proposition, confidence, source, observed_at,
             expiration?, visibility, belief_or_verified_fact}
HistoricalEvent {id, world_date, actual_fact_refs, actor_ids, place_ids,
             action_id, causes[], changed_entities[], generation_provenance,
             severity, audience, chronicle_type}
RuleDef     {id, version, trigger_keys[], role_queries, guards[], proposals[],
             actions[], followups[], cooldown, provenance, effective_from, status}
DirectorProposal {id, generated_at, depends_on, proposed_for_date,
                  claims, scope, intervention_kind, cost, outcome, audit}
```

`Person` 的字段不必全部存在同一数据库表；这是领域契约，不是建议一张巨型 JSON 表。高频列式状态和稀疏关系/历史可分表。**任何对象引用都必须用稳定 ID，不用日志文字查找人物身份。**

### 2.2 必须永远成立的不变量

1. **人口守恒：** 聚合人口 + 从其中展开的具名人物 = 实际人口；人口流入/出生/死亡/迁移都有对应账本；展开 NPC 不可凭空制造人数。
2. **钱/物资守恒：** 实际财富与货物交易有支付方和接收方；工资、救济、军需和补贴不能无来源增加。宏观生产/税收/资产估值可以在明确定义的模型下改变总量。
3. **唯一历史：** 同一世界同一事件只能结算一次，采用幂等键；历史一旦提交不可追溯改写。
4. **时间因果：** 无法在死后参加真实谈判；不能从未来知悉未发生的事实；Director 不能把日期推回到影响已提交事件的时间点。
5. **独立意志：** 请求发起人与受邀者分别做决定，不能单方面让对方已签婚约、已被说服或已转移财产。
6. **信息隔离：** 人物知道的事实和世界真相分离；超常能力若突破认知边界要通过合法机制；玩家不可读取隐藏人生预演或别人的私人策略。
7. **年龄与身体：** 婴儿需要监护，伤残影响具体能力，死亡是终止大部分普通行为的状态（特殊复活/鬼魂另有世界机制）。
8. **规则版本：** 新事件不能改变已有历史事务在原版本下发生的事实；未完成 Project 的规则升级应按迁移策略处理。

## 3. 精确说明人与社会怎样共同结算

### 3.1 从聚合人口中生成真实 NPC

以某地区 `PopulationCell` 中的青年工人 8,000 人为例，工厂雇佣名单可同时引用：`7,995 名匿名聚合人员 + 5 名具名人物`。当某普通工人成为玩家人物的关键朋友，采用一次 `materialize` 事务：原 cell 减一、创建唯一 Person 和合法的家庭/就业/人口来源引用、写入 provenance。之后他永久具名，不因玩家不在线又被自动“合并回”人口并删除关系。

玩家创建的孩子则走出生账本：若宏观出生人数已经批量结算，从该批新生儿库存中提取一个并提升身份；否则出生事件同时增加真实人口与 Person，不可在两个系统各加一次。**历史人物预定出生**也遵守同一原则，且需双亲/地点/当前历史条件成立。

### 3.2 三种调度精度，不复制三套规则

**聚合结算：** 每月/季度，POP 年龄转移、婚育、死亡、迁徙、工资和消费、产业/战争产出；数十亿普通人口也可以使用地区/年龄/职业组合单元，而非逐人刷新。

**具名人物常规结算：** 按到期时间、生日、项目阶段、疾病风险、家庭变更、重要接触事件处理；人平时仍维持状态，但不每模拟天调用决策或 LLM。

**关键场景：** 两人重要谈判、法庭案件、军职抉择、婚姻重大分歧、政治阴谋、特殊能力使用，可进入精细多方事务，保存双方信息、行动及回应。

某次战争事件同时影响聚合 POP 的补给/死伤，及具名士兵的具体健康与社会关系，最后通过账本对账，不能分开独立抽伤亡。

### 3.3 人与人相遇：从地点与关系构建候选集合

关系网络应当来自家庭、场所与事务，而非全世界随机连边。以 `place_presence`（学校班级/工作班次/医院/军营/公共会议）、`membership`、`relationship`、`project_participants` 和 `travel_itinerary` 索引提供候选；优先共享近邻和真实关联。若另一人只是名字出现在历史目录里、时间地点不符合，他不会自动进入候选。

互动流程：

```text
社会场所/事务给出候选接触人
  → 依据双方所在地、时间、权限、认知生成可以提出的行为
  → 发起人选择/提出请求（程序常规行为或 LLM 特殊策略）
  → 写 PendingInteraction
  → 接收人收到请求，根据自己的认知和意愿答复或反提案
  → 共识/拒绝/拖延/冲突产生 Outcome
  → 已经提交的改变成为双方关系、家庭、组织和历史的一部分
```

长期相识不需要每次重新生成一次聊天；日常维护关系可以按共同生活时长和关键事件更新。

## 4. 统一规则执行机制：不要只做 `+trait` 的假引擎

建议采用 **已知实体 + 有限类型的状态效果 + 可组合事务/过程 + 触发规则**。可以借鉴 Cataclysm:DDA EOC 的周期/事件驱动与作用域、Wildermyth 的角色约束/历史改变、CK3 的 on_action/scope、FreeSO 的行为脚本/交互队列，但不直接照抄任何一个世界状态模型。

### 4.1 可执行内容至少要支持六类语义

- `query`：带索引的实体查询、关系图查询、位置时间窗、群体/角色过滤。
- `guard`：状态、知识、组织权限、资源、社会规则、历史年代与冷却条件。
- `offer/action`：人或组织可以尝试做什么，谁需要回应。
- `process`：持续申请、就业、科研、贸易、战线、治疗、组织计划，可中止和重排。
- `effect`：资源转移、伤害与恢复、建立/取消关系、赋予职位、修改组织、启动新 Project、对人口施加政策或地区过程。
- `followup/history`：延迟事件、版本化规则、个人记忆、完整因果链接与可读历史。

不限固定十个原语，但新效果必须有清晰的资源与权限边界。不能把一个全局任意 `set` 暴露给 LLM。

### 4.2 可供实际编译的事件例子

```yaml
id: labor.injury_claim
version: 3
on: employment.injury_confirmed
scope: workplace
roles:
  worker: {ref: event.worker}
  employer: {ref: worker.employment.org}
  doctor: {query: {has_role: licensed_physician, place: worker.current_region}, optional: true}
  union: {query: {member_group_contains: worker, kind: labor_union}, optional: true}
requires:
  - {op: alive, ref: worker}
  - {op: existing_contract, between: [worker, employer]}
offers:
  worker:
    - submit_compensation_claim
    - waive_claim
  employer:
    - offer_settlement
    - contest_claim
    - request_medical_assessment
process:
  create: legal_claim
  parties: [worker, employer]
  target_jurisdiction: {ref: worker.workplace.jurisdiction}
  deadline_policy: jurisdiction_labor_claim_limit
outcomes:
  agreement: [transfer_existing_compensation, record_settlement]
  contested: [schedule_hearing, update_participants_beliefs]
  no_claim: [close_case]

# 注：示例契约，尚非现有引擎实际支持的 YAML。
```

这里的 `doctor` 只能从存在的、具资格的人中匹配。`schedule_hearing` 创建一件真实未来事务，不能直接宣布申请人赢官司。若地区法律没有赔偿途径，事件从一开始就不应提供不合法的司法选项。

### 4.3 规则发布管线与索引

`Draft → Schema Parse → Static Type Check → Scoped Query Check → Guard/Effect Check → Invariant Check → Synthetic Fixture → Staged Active → Active`。这是**自动发布**，不需要人工审核。`Staged Active` 可只表示先编译并原子替换指针，而非人工批准阶段。

基于 `trigger_key → rule_ids`、地区/年代/职务/组织类型/人口标签二级索引匹配候选，之后才做昂贵条件检查。禁止每模拟日 `N 人 × 全部 R 条规则` 双重扫描。新事件入库之后在索引层增量生效，支持撤销新版本/隔离异常规则，不删已提交事实。

动态内容缺口应从世界事实驱动：新技术出现、组织人数激增、某类事务失败率升高、事件匹配覆盖极低、重要历史变更、玩家祝愿引入新可观察行为。避免无目的地每隔一分钟凭空生成 1,000 个随机事件。

## 5. 深度出生编译 Life Contract

### 输入

`WorldSnapshotRef`（当前日期、地区法律、家庭与监护、技术、社会环境、宏观历史、已存在的重要人物及组织）+ 用户创建信息 + 原始祝愿。

### 生成成果

1. **语义解释与可见摘要**：这句祝愿到底是美好期望、实际超常能力、讽刺/诅咒、私有任务系统还是矛盾愿望；允许多种可能性，但提交前必须给出明确实现版本。
2. **出生事实**：身体与先天条件、家庭归属、出生地点和时间；由 World Runtime 最终认定。
3. **私人 Life Program**：目标候选、价值倾向、长期兴趣、学习/交往策略、对特定压力的条件式反应；规则与人物历史可结合。
4. **隐藏 Life Forecast**：若干不同世界条件下可能发生的轨迹与失败方式，只作预测和个人未来反思，**不是事件时间表**。
5. **Wish Capability Contract**：触发、作用对象、范围、代价、冷却、认知权限、执行效果、成长/失效/被压制机制。
6. **Provenance**：模型、规则版本、上下文摘要哈希、编译日期、用户输入哈希、编译校验结果。

### 原子出生事务

先异步编译后进入 birth-reservation 队列；在**实际提交**时重新确认父母仍存在、监护条件、当前世界日期和人口账本。若父母已死/迁居，应重新选择合法家庭并必要时重编出生上下文，不可拿过期 LLM 结果强行写入当前世界。用户提交出生到孩子正式出生可能存在排队延迟，但不能直接回退为无 LLM 的普通模板出生。

## 6. LLM 角色与权限边界（可操作版本）

| 角色 | 何时调用 | 可提交 | 不可以 |
|---|---|---|---|
| Birth Simulator | 每个玩家出生 | 祝愿解释、生命预演、个人规则 | 确定几十年后事实；凭空抢夺他人身份 |
| Life Replanner | 战争失亲、失业、改信仰、计划不可行等显著转折 | 未来目标/行为策略新版本 | 修改已经发生的经历 |
| Conflict Deliberator | 稀有复杂互动、重要政治决策、异常能力使用策略 | 双方要提出的行动、意图、陈述 | 直接宣称另一方已同意或已死亡 |
| Content Author | 发现内容缺口和新社会现象 | 编译用事件族、触发、角色、行为、流程定义 | 向生产 DB 发 SQL；执行任意代码 |
| Historical Director | 重大世界变化与导演周期 | 外生冲击、主动邀约、政治危机、罕见历史巧合 | 清除之前事实；强行规定战争结局 |
| Life Summarizer | 人物死亡归档后 | 事实引用的最终生平与祝愿对照 | 编造英雄事迹、感情关系或历史人物会面 |

### 强导演的特殊权力

可创建**真正的新原因**：例如跨国外交活动、事故/灾害源、经济供需冲击、政治宣传机会、科学发现的机遇、相遇的邀请链与交通安排。不用要求它完全被既有社会过程被动触发。但仍必须：限定影响范围、验证前提、生成来源审计、成本与强度预算、预定将来生效、执行后遵守同一物理和社会过程。干预可偏向历史回归，却不能直接提交 `1914 年必须爆发一战`。

### 运行期新机制扩展的两种边界

- **规则组合扩展：** 用已支持的脚本结构、事务和效果自动生成新内容，通过编译测试后即刻发布。这是常态。
- **底层执行器扩展：** 真正新型数据结构/物理规律/结算器需要更改生产代码；可交给 Coding Agent 生成补丁、在隔离环境进行构建和迁移测试，再进入独立部署流程。**不允许直播世界自动运行未经隔离审核的任意生成代码。** 这条与“LLM 事件自动发布”并不冲突。

### 预算与公平

世界级 token budget 按 `birth / personal_replan / world_content / director / death_summary` 分队列，支持 token 上限、优先级、缓存与重试。强制限制每人/每世界同一时间窗的深度调用次数，但为无名普通玩家保留最低可用资源，不让 LLM 只偏爱著名人物或富豪。相同知识与内容族缓存复用，但个人预演不能简单复制他人的整段未来。

## 7. 30/60 秒一年：真正的计算契约

### 7.1 不是模拟中每天真实睡 82 毫秒

内部世界时间用模拟 `day_index` 或精确日期、离散事件队列推进。**真实墙钟只控制对外可见的目标世界速度**。某个模拟日没有事件可以直接跳过，重要事件能按日期排序，宏观人口可按月/季批量运算。不要每“世界日”逐角色扫描。

- 测试倍率：30 秒/年，月约 2.5 秒；60 秒/年，月约 5 秒。
- 离线跑数：尽可能快跑完整世纪；保留同样规则和同样历史事件产物，不与网页渲染绑定。
- 生产：倍率从独立的 `TimePolicy` 表读取，可调；不应该在法律、教育、战争或个人记忆代码中直接出现 30 或 60。
- UI：每几秒拉取新章节，用户可以回看之前的日志；历史阅读进度独立于当前世界时间。

### 7.2 以 20k/40k 具名人物计算热点

假设每名具名人物每模拟月平均一次基础状态触发：

- 20k 人 × 12 月 / 30 秒 ≈ **8,000 次人物月激活/秒**。
- 40k 人 × 12 月 / 30 秒 ≈ **16,000 次人物月激活/秒**。
- 如果每名人物每模拟年产出一条永久历史记录，20k 人的 30 秒/年相当于 **667 条历史记录/秒**；一天最多 **5,760 万条**，每条平均 500 B 是 **28.8 GB 原始数据/天**，还不含索引/备份。这不是建议的记录密度，而是上界警告。

因此**常规状态更新不写成逐条日志**；按脏集合批量落库，常规行为汇总为里程碑/持续时间，在未影响未来的操作上不制造永久故事。真正的出生、死亡、婚姻、迁徙、组织更迭、创伤、法律改变等仍要可追溯。存储预算用“每 100 模拟年/每世界”而不是只看每真实天；如有大量赛季归档，仍需冷存储策略。

### 7.3 VPS 预算

用户提供服务器：6 共享 vCPU、13 GB RAM、113 GB NVMe，长期平均 CPU ≤30% 总机（约 1.8 个 vCPU 等效），24 小时满载仅允许短时。**这是一个运维约束，不应宣称全系统能稳定占 1 核。**

- 权威模拟器尽可能采用单写者，内存增量索引，热点状态缓存，少写数据库；多线程主要用于离线预处理与旁路任务。
- 浏览器/公开章节与静态资源由 CDN 缓存，个人记录走鉴权 API；轮询最新章节，不要求 WebSocket。
- LLM 推理使用外部 API，设限流、并发池、超时与熔断。异步任务带 `depends_on_state_ids + revision`，提交前检查对象版本，避免世界前进导致过期计划偷改事实。
- 后台归档、索引维护、规则编译分散执行，不与推进世界的计算尖峰叠加。
- 需要外部备份；同一台 VPS 的复制不是灾备。

### 7.4 已进行但有限的实验

当前会话运行了已有 `sim_kernel_load_probe.py` 合成内存调度探针：20k 人、约 14.7 万有向关系、8k 规则、1 模拟年，约 1.13 秒墙钟；40k 人、约 29.4 万有向关系，同规则约 2.91 秒。环境为当前容器的 Python 单进程；仅索引、定时触发、简化关系与筛选，**没有数据库、真实人际因果、战事、LLM 或异地存储**，不能用这些秒数推导实际 VPS 容量。合成数据里每个人每月更新一次已经包含了 12 次左右激活。实验源码附在交付包，可重跑。

## 8. 人口规模与快时间的人物供给（不可回避的产品数学）

在 30 秒/年下，100 年世界只存在 **50 分钟**，70 年人生约 **35 分钟**，现实一天跨越 **2,880 个游戏年**。即使模拟可以处理 40k 名具名人物，也不表示有足够多的真实玩家持续补充孩子。

假设想长期维持 10k 个**同时存活的玩家角色**，且平均存活 70 年，则需要每模拟年 10,000/70≈143 个新玩家孩子，按 30 秒/年即 **约 17,143 次真实注册出生/小时**。60 秒/年仍约 **8,571 次/小时**。死亡率及实际加入时段变化会使数字波动。

建议将 **10k+ 玩家注册人物/一世界历史累计** 与 **10k+ 同时存活玩家人物**列为两个不同容量指标。用户没有要求持续 24h 同时活着的 10k 账户角色，因此不应为了名义人数偷偷制造不死小人或免费补人。若未来确实要求后者，需改变正式世界速度、赛季加入结构或运营规则；不是单靠优化引擎就能实现。

测试阶段完全可以选 300、1,000、3,000 名具名人物 + 完整 POP、全机制跑 100 年；**不要删掉机制**，只改变数据密度、角色实例化规模、地图关注区域和目标时钟。

## 9. LLM 数量级成本（不得口头说“可忽略”）

举例，单名出生编译假设 8,000 输入 tokens + 2,000 输出 tokens（**容量假设，不是推荐 prompt 大小**）：

- 10,000 个注册出生 ≈ 8,000 万输入 + 2,000 万输出 = **1 亿 tokens**，尚未算重试和重规划。
- 若人均 70 模拟年固定触发一次深度规划，在 20k 同时存活、30 秒/年下是每模拟年 20k 次 → **每天 5,760 万次调用**，根本不适合。
- 只有「按事件重要性与个人预算触发」+「内容族共享复用」+「离线批量编译」才能控制调用量。出生编译不可被无 LLM 规则替代；如调用量不足，新增出生进入待处理队列，并明确前端告知排队，世界不暂停。

运营成本公式：`总价 = 输入总 tokens × 输入单价 + 输出总 tokens × 输出单价 + 重试 + 基础设施`。模型和接入商的当前价格、限流、缓存折扣需要实际测量，不能写死估价。

## 10. 权威世界单写者、事件日志与档案

### 10.1 内存执行与写入

1. 从时间队列取到期宏观批处理、项目阶段、人物接触、能力冷却、战争/死亡事件。
2. 构造只读决策快照，产生动作提案（本地规则优先、少数任务异步 LLM）。
3. 由权威 Resolution 依次验证前提和资源；涉及多个实体的操作原子执行。
4. 写入状态日志（能恢复），按历史显著性额外写 ChronicleEvent（给人看）。
5. 更新二级索引、下游事件订阅、下一次到期任务。
6. 定期生成状态 Snapshot，保留世界 seed、规则版本、LLM 已提交输出以支持回放。

`State Journal` 与 `Human Chronicle` 必须区分：不是每笔微小流转都要成为人生记录，也不能仅靠精美日志恢复世界状态。建议 DB 初期以 PostgreSQL 为中心，压缩归档与不可变大日志迁移到廉价对象存储；实际结构依据已有仓库实现选择，避免推倒重写。

### 10.2 多人一致性与内容即时发布

所有角色同世界数据库、同一世界时间、同一权威提交者。新增 LLM Rule 在 `effective_from >= next_safe_boundary` 时生效，不溯及过去。跨人事务采用对象版本与幂等键，不能简单使用 `global_revision`，否则无关城市的一次交易也会废掉大批 AI 计划。规则索引按版本热更新，正在执行的事务可继续使用其锁定版本或显式迁移。

### 10.3 可缓存的公共页面

公共章节/世界地图状态使用不可变 URL 例如 `/public/world/<id>/chapter/<n>.json`；`/latest` 短缓存/条件 GET；人物私人记忆、出生草稿和预演结果绝不能进入公共缓存。Cloudflare 对 JSON 需要显式适配 Cache Rules，不可只靠 `immutable` 假定所有 JSON 已边缘缓存。

## 11. 历史事实、伪造内容及安全

- 1900 baseline 的来源和确定度必须跟随资料项；历史人物的行踪不详时允许虚构合理补全，但要以“游戏架空内容”标注，不是史实。
- 新剧情和规则数据标识生成模型与生成时间，不能把虚构的历史人物语录写成真实引文。
- 1900–2050 可能涉及真实屠杀、殖民暴行、战争与仇恨政治；模拟不能把民族、宗教或现实受害群体天然设为负面属性，也不把残酷历史改成娱乐化虐杀日志。
- 自由祝愿和事件文本是非可信输入；严格结构化输出解析、作用域限制、无任意 SQL/文件/网络/代码执行。公开文本有平台内容治理，不能任由其他玩家通过输入注入系统指令。

## 12. 关键能力的验收方式（自动化而非让玩家不停手动测）

**合格不是“225 项测试通过”，而是完整因果运行。**

A. 父亲工伤后：若企业赔偿成功，孩子可能继续读书；若失败且储蓄不足，家庭真实面临工作/借贷压力。同一事件驱动家庭、就业、学校、法院与组织，不硬编码 Anna 的结果。

B. 两名真实玩家人物：同校/同工厂/同军队的接触几率高于无关联随机人物；对同一请求双方可以作不同选择，形成长期记忆和后续事务。

C. 制度从无到有：通过几十年真实组织行动产生工伤法，法条生效后新的受伤事件自动出现更多法定手段；删除 LLM 仍能执行。

D. 超常能力：区分故意谎言和真诚误信，消耗真实记忆，关系改变；使用同一事实事件跨人可查询不同主观认知。

E. 强导演：可以成功引入合理的外生冲击/历史人物聚会机会，实际人物可拒绝，所有干预记录 provenance，不能改过去。

F. 灾难战争：宏观人口伤亡与具名人伤亡完全对齐，不会一个士兵死两次；新的难民迁徙会真实改变学校、工作、医院和两地关系网络。

G. 长期历史：同一随机种子 + 相同外部 LLM 生成结果 + 相同规则版本应能复现；快进、保存/恢复、断点继续与正常步进的状态哈希一致。

H. 性能：分别记录 300/3k/20k/40k 具名人物、不同社会网络密度、不同事件库规模下 CPU 平均/峰值、DB 写入、内存、历史磁盘增长、LLM tokens；目标按现有 VPS 实际预算确定，不能用合成探针声称已达标。

## 13. 执行顺序（现有仓库增量升级）

1. **先读取真实源码：** 人物生命周期、家庭/POP 结算、关系存储、组织/战争、事件执行器、LLM 接口、事务/历史、Web。输出保留/需补/必须重构的判定和证据路径。
2. **稳定人口守恒和跨人事务：** 因为这两处不成立，之后新增任何事件都会放大错误。
3. **成熟的规则索引、作用域、多角色匹配与延迟执行：** 先把底座统一，再让 LLM 写事件。
4. **Birth Contract + 特殊祝愿编译：** 必须真实进入现有人口、家庭、能力、人物认知模型。
5. **历史与社会内容生产流水线：** 开发期大量生成实用事件族，运行期有条件自动扩展。
6. **宏观历史与具名角色双向反馈、强 Director：** 不断改写后续机会而非播放史实。
7. **完整人生观测与运行优化：** 当前三栏 UI 只读权威日志，持续增强像素纸娃娃、人物履历与回放。
